# S1 — libmpv under a transparent webview

**Status:** done (Windows; macOS/Linux CI-only per D64) · **Dates:** 2026-10-14 → 2026-10-14 · **Plan:** [S1](../plan/phase-0-spikes.md#s1-libmpv-under-a-transparent-webview) · **Spec:** [player-backend](../specs/player-backend.md) · **Decision:** D64, D65, D66, D67, D68

## Question
Can the desktop shell show a web UI over native mpv video? Exit criteria:
- Windows: no tearing; correct HDR10 output on an HDR monitor (`gpu-next`, d3d11); resize without flicker; web OSD over video at 60 fps.
- macOS and Linux: same, or a documented fallback (separate borderless player window) that works.
- Verdict logged as a D#: **Tauri v2 vs custom shell** (stremio-shell-ng style).

Scope (D64): Windows tested end to end on the owner's PC; macOS/Linux built in CI only.

## Verdict
**Tauri v2 works; no custom shell needed (D67).** On Windows, mpv embedded with `wid` under a transparent WebView2 passed every criterion on the owner's 4K 240 Hz HDR monitor:
- mpv outputs HDR10 through a PQ / BT.2020 swapchain and hands it the source's MaxCLL, and the owner confirmed it looks like HDR. Whether the monitor receives that metadata isn't verified (Windows doesn't guarantee it).
- No tearing.
- Resize, fullscreen and minimise stay smooth.
- The web OSD holds the full 240 fps (p99 4.4 ms) over 4K HEVC HDR video.

The only Win32 code beyond Tauri is about 40 lines that keep mpv's child window under the webview. Two things to carry into Phase 1:
- The SDR UI looks too bright over HDR video. Fixed in-app with OSD dimming (D68).
- One unreproduced hang in 8 transparent-window stress runs.

macOS and Linux were only built in CI; their plan stays the separate-window fallback until tested on hardware (D64).

## Prior art (T0.S1.1)
Read 2026-10-14 from source. Repos: [stremio-shell-ng](https://github.com/Stremio/stremio-shell-ng), [Rillio](https://github.com/pek100/rillio), [stremio-linux-shell](https://github.com/Stremio/stremio-linux-shell), [tauri-plugin-libmpv](https://github.com/nini22P/tauri-plugin-libmpv), wry/tao sources, mpv `render.h` and manual.

**The one fact that shapes everything:** libmpv's render API only has OpenGL and software backends (`render.h`: `MPV_RENDER_API_TYPE_OPENGL`, `_SW`; no d3d11/Vulkan). `target-colorspace-hint` (HDR passthrough) needs `vo=gpu-next` with a d3d11, Vulkan or Wayland context. So **HDR passthrough requires mpv to own its window** (embedded via `wid`), not the render API.

| | stremio-shell-ng (Windows) | Rillio (Tauri 2) | stremio-linux-shell |
|---|---|---|---|
| Shell | native-windows-gui + `webview2` crate | Tauri 2 (tao + wry) | GTK4 + WebKitGTK |
| mpv embedding | `wid` = top-level HWND; mpv creates its own child | `wid` = Tauri HWND, then the `"mpv"` child is moved to `HWND_BOTTOM` | render API (OpenGL) into a `GtkGLArea` |
| Web layer | windowed WebView2 controller, background RGBA alpha 0, top-level not transparent | Tauri window `.transparent(true)` | `GtkOverlay`, WebKitGTK background alpha 0 |
| HDR | `gpu-next`, d3d11, `target-colorspace-hint=auto`, switches HDR/SDR settings when the display's mode changes | `gpu-next`, `target-colorspace-hint-mode=source` (`target` + sRGB ICC gave washed-out grey) | none (OpenGL) |
| macOS / Linux | n/a | no embedding: mpv gets its own window | X11 + Wayland both work |

Other findings:
- **Windows needs no DirectComposition or layered windows.** A transparent WebView2 (`DefaultBackgroundColor` alpha 0; only 0 or 255 is allowed) "renders hosting app content as the background", and that includes a sibling child HWND drawn by mpv. wry uses this same windowed controller. One Rillio comment says a transparent *top-level* hides GPU-rendered children, which conflicts with its current default; we test both window modes.
- **Z-order is fragile.** mpv recreates its child window on VO re-init, so the shell must push it to the bottom again each time.
- **Input:** mpv must not take keyboard/mouse (`input-vo-keyboard=no`, `input-cursor=no`); the webview owns input.
- **Known issues:** white flash before the WebView2 background is applied (the `WEBVIEW2_DEFAULT_BACKGROUND_COLOR` env var avoids it); raised black levels (stremio-shell-ng #104).
- **macOS:** the manual lists `--wid` for X11, win32 and Android only, and mpv's mac VO doesn't appear to read it. Embedding means the OpenGL render API into a layer under WKWebView (IINA-style): deprecated API, no HDR/EDR passthrough.
- **Linux:** `wid` only works on X11/XWayland and WebKitGTK over a foreign X child is reported broken. The working route is stremio-linux-shell's GTK4 `GLArea` + render API; Tauri is GTK3/webkit2gtk-4.1, so Tauri would need its widget tree rebuilt around a `GLArea`. No HDR either way.
- **Crates (2026-10-14):** tauri 2.12, wry 0.57, `libmpv2` 6.0 (maintained; stremio-shell-ng uses it). The spike loads `libmpv-2.dll` at run time instead (see below).

### Approach per OS
| OS | Embedded approach | HDR | Fallback (D64: documented until tested) |
|---|---|---|---|
| Windows | Tauri window; mpv `wid` = window HWND; mpv child at `HWND_BOTTOM`; WebView2 background alpha 0. Test transparent and opaque top-level | `gpu-next` + d3d11 + `target-colorspace-hint`, through DWM | separate mpv window (Rillio's `RILLIO_EMBED_MPV=0`) |
| macOS | OpenGL render API into a layer under a transparent WKWebView | none (SDR tone-mapped) | **separate borderless mpv window** (own NSWindow, HDR/EDR possible) kept under/behind a transparent web window |
| Linux | GTK `GLArea` + render API under WebKitGTK (stremio-linux-shell) | none | separate borderless mpv window (works on X11; Wayland can't position it) |

## What we tried
Code: [`spikes/s1-shell/`](../../spikes/s1-shell/) (own Cargo workspace, D65; its README says how to run it).
- **Shell:** Tauri 2, window built in `setup`. Two window modes:
  - `transparent`: Tauri transparent window, as Rillio does.
  - `opaque`: normal window with webview background RGBA 0, as stremio-shell-ng does.
  - `WEBVIEW2_DEFAULT_BACKGROUND_COLOR=00000000` avoids the white flash.
- **libmpv:** loaded at run time with `libloading`, so CI builds without libmpv. About 200 lines of FFI cover the dozen calls needed. The build is the pinned mpv-project MinGW `v0.41.0-dev-g270367e8a` (GPL), fetched and SHA-256-checked by `tools/fetch-libmpv.mjs` (D66).
- **Embedding:**
  - `wid` = Tauri's HWND, with `vo=gpu-next`, `gpu-context=d3d11`, `hwdec=auto-safe`, `target-colorspace-hint=auto`, `hint-mode=source`; mpv input off.
  - After each `VIDEO_RECONFIG`/`FILE_LOADED`, the shell walks the window's children and moves class `"mpv"` to `HWND_BOTTOM`.
  - Resulting window tree: `WRY_WEBVIEW` above `mpv`, both sized to the client area.
- **OSD page:** plain HTML/JS with no build step. It polls mpv properties and records every `requestAnimationFrame` delta while a test phase runs. A probe ball moves every frame, so web-layer judder is visible.
- **Stress driver:** Rust drives the window while the page measures: a size sweep every 16 ms, a fullscreen toggle every 1.5 s, and a minimise/restore loop. `--auto stress` runs everything unattended and saves JSON.
- **Media:** generated locally by `tools/make-media.mjs` (ffmpeg). With synthetic clips we know exactly which metadata should arrive.
  - `hdr10-bars.mkv`: 4K60 HEVC Main10, PQ/BT.2020, mastering 1000 nit, MaxCLL 1000 / MaxFALL 400.
  - `sdr-bars.mkv`: the same pattern in SDR.
  - `tearing.mkv`: a white bar sweeping 32 px/frame at 60 fps.
- **Also tried:** `hint-mode=target`, hint off, and `--no-embed` (mpv in its own window).

## Surprises & gotchas
- **It just worked.** A windowed WebView2 with an alpha-0 background shows the mpv child window under it in both window modes, with no DirectComposition or layered windows. Rillio's comment that a transparent top-level window hides GPU-drawn children doesn't hold for Tauri 2.12 + current WebView2.
- **HDR passthrough survives DWM composition.** mpv's d3d11 swapchain in a child HWND switches to PQ, and DWM composes the SDR webview over it at the SDR white level. Fullscreen and minimise toggles recreate the swapchain, which briefly goes back to sRGB before switching to PQ again.
- **The judder isn't caused by compositing.** The owner saw a slightly jittery bar in the S1 shell and the same jitter in plain mpv in its own fullscreen window. Likely cause (a hypothesis, not measured): 60 fps content held for 4 refreshes on a 240 Hz screen. Measuring frame timing and tuning it (`display-resample`, interpolation) is Phase 1 work (T1.7.11).
- **One hang.** 1 of 8 transparent-window stress runs never saved its results: mpv kept playing, but the page stalled somewhere in the stress phases. It didn't happen in 7 more runs, including after page-side logging was added. Watch for it in Phase 1.
- **WebView2 doesn't throttle rAF while minimised** in this setup: no gaps over 500 ms appeared during minimise phases.
- `frame-drop-count` resets when the VO re-initializes, so its change across a fullscreen toggle can be negative.
- ffmpeg's `drawbox` evaluates `x` only once, so the first tearing clip had a bar that never moved (the owner caught it). `overlay` re-evaluates every frame.
- Windows 10+ has `tar.exe` (bsdtar, reads zip) in System32, but Git Bash puts GNU tar first on `PATH`, so call it by full path.

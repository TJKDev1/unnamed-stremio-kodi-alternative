# S4 — Core ↔ UI IPC

**Status:** done (PC + CI; the LG C3 number comes from S2, D69) · **Dates:** 2026-10-14 → 2026-10-14 · **Plan:** [S4](../plan/phase-0-spikes.md#s4-core--ui-ipc) · **Spec:** [view-model-ipc](../specs/view-model-ipc.md) · **Decision:** D69, D70, D71, D72

## Question
Can the core push view-model updates to the UI fast enough for 60 fps? Exit criteria:
- < 2 ms per frame for patch encode + transport + apply at typical load (home screen with 10 rows streaming in).
- Same patches work over Tauri IPC and over WebSocket (remote core).
- Verdict logged as a D#: patch format and encoding (MessagePack vs postcard vs other).

Scope (D69): measured in WebView2 on the owner's PC and in headless Chromium 94 in CI. The C3 measurement happens in S2, which builds an IPK anyway. Two diff methods × three encodings (JSON as the baseline).

## Verdict
**Yes, with room to spare.** At typical load, a frame costs **0.6 ms p95 over WebSocket and 1.4 ms p95 over Tauri IPC** end to end (core diff + encode, transport, decode, apply incl. Solid's DOM updates) with the typed diff, on the owner's PC in WebView2; 1.8 ms p95 over WebSocket in headless Chromium 94 on a CI runner. Every run over every transport ended with the UI's view-model identical to the core's.

Decisions:
- **Patches are typed ops, generated from the view-model schema** (D70): keyed list edits (remove / move / insert) and one set per changed field. 3× cheaper in the core than a generic tree diff (0.13 vs 0.40 ms p95) and smaller.
- **Encoding: JSON for now** (D71). `JSON.parse` is native and as fast as anything we can write in JS; MessagePack's JS decoder was the slowest and its frames barely smaller, so it's dropped. Postcard frames are 2–4× smaller and decoded as fast here, but it's positional (core and UI must share the exact schema version). We re-measure JSON vs postcard on the C3 in S2 and switch only if JSON is the bottleneck there.
- **Desktop transport: Tauri IPC** (D72), pushed through a Tauri `Channel` in Phase 1. WebSocket only for a remote core. WebSocket was the faster transport (0.3 vs 1.0 ms round trip), but both fit, and Tauri IPC opens no port.

The worst case we tried (a full 10 × 50 home, then reshuffling every row) costs ~3 ms p95 per frame, almost all of it Solid creating and moving 500 card DOM nodes. That's S2's subject (virtualized rows keep ~12 nodes per row).

## What we tried
Code: [`spikes/s4-ipc/`](../../spikes/s4-ipc/README.md) (own Cargo workspace and pnpm root, D65).

- **View-model and load (T0.S4.1).** `Home { rows: [Row { id, title, loading, cards: [Card { id, title, poster, year, progress, badges }] }] }` and three intents (`MarkWatched`, `LoadMore`, `HideRow`). Two deterministic scenarios: **stream** (typical): 10 addon rows appear over 1.5 s and fill in 3 chunks each (50 cards; every third row is ranked, so cards land mid-row), with progress and badge updates, a row moved to the top and one hidden; **refresh** (worst case): a full 10 × 50 home in one frame, then two frames that reorder every row and change a third of the progress bars.
- **Diffs (T0.S4.2).** One patch per frame from the previous frame's snapshot (several changes in a tick → one patch). A shared keyed list diff (ids) emits remove / move / insert and the items to compare in place.
  - **Generic:** `serde_json::Value` tree of the whole view-model each frame, path-addressed ops (`Set`, `Unset`, `Insert`, `Remove`, `Move`). Works for any view-model, readable without a schema.
  - **Typed:** hand-written here, generated in the app: `RowInsert`, `CardMove`, `CardProgress { row, card, progress }`… one op per changed field, index-addressed.
  - Both are property-tested: `apply(diff(a, b), a) == b`.
- **Encodings (T0.S4.3).** JSON (serde_json), MessagePack (rmp-serde, struct maps, so JS gets the same objects as from JSON), postcard (hand-written JS decoders; generic ops carry explicit value tags).
- **Transports (T0.S4.4).** A Tauri v2 shell answering `invoke` with raw bytes (`tauri::ipc::Response`, no JSON wrapping), and a WebSocket core (tungstenite) that the same page talks to. Same control messages on both. Frames are *pulled* (one request per frame) to time everything on one clock; the app will push.
- **UI store (T0.S4.5).** A SolidJS store; each frame's ops apply inside one `produce`, rendered by `<For>` rows of cards (no virtualization). The page sends the same three intents after frames 10, 25 and 40 on every transport, then checks its final view-model against the core's.

## Surprises & gotchas
- **One `splice` on a Solid store array notifies every index after it.** Applying a reshuffle as ~450 sequential moves took ~5 ms in the store alone. Applying a frame's structural edits to a plain working copy of each array (holding the same store proxies) and assigning it once took that to ~0.5 ms, and `<For>` still moves the existing DOM nodes. Field sets keep going through the proxies, so only touched cards re-render. This goes into the spec as an apply rule.
- **Tauri IPC is slower than a localhost WebSocket in WebView2** (~1.0 vs ~0.3 ms round trip p95). Tauri v2's `invoke` goes through a custom-protocol request in WebView2. Fine for the budget; pushing via a `Channel` (Phase 1) skips the request leg.
- **Measure after paint.** Starting a frame's clock right in the rAF callback put the browser's layout and paint of the previous frame into "transport" (the reply waits for it): refresh frames showed 6–11 ms "transport". Starting from a task queued in rAF (runs after the paint) fixed it.
- **The MessagePack JS library is slower than `JSON.parse`** for our object-heavy frames. Native JSON parsing in V8 is hard to beat from JS.
- **Postcard can't carry untagged values**, so generic ops (strings or numbers in paths, any JSON as values) need explicit tags; a positional format really wants typed ops.
- **Timer resolution is 0.1 ms** in both Edge and WebView2 (no cross-origin isolation), so per-frame decode/apply under 0.1 ms isn't resolvable; the p95 and the replay means are what to compare.

## Consequences
- **Decisions logged:**
  - D70: patches are typed ops generated from the view-model schema; keyed list edits + per-field sets; one patch per frame; the UI batches structural edits per array.
  - D71: JSON encoding for now; MessagePack dropped; JSON vs postcard re-measured on the C3 in S2.
  - D72: desktop UI ↔ embedded core over Tauri IPC (push via `Channel`); WebSocket only for a remote core.
- **Specs to update:** [view-model-ipc](../specs/view-model-ipc.md) stub → draft (patch ops, encoding, transports, apply rules, frame header, conformance tests). `sdk-schema` (T1.1.2) must generate the typed diff (Rust), op types and apply (TS) from the schema.
- **Plan changes:** S2 gets a task to re-run S4's decode + apply replay on the C3 (JSON vs postcard). T1.1.2 now includes diff/apply codegen.
- **Code to keep:** the keyed list diff (`keyed.rs`) and its property test; the apply-with-working-copies approach in `store.ts`; the frame header idea (core timings in every frame, for a debug overlay). The rest is rewritten in Phase 1 against the generated schema.
